# DocTrust evaluation — results

> **Status: RUN, results below.** The protocol and report format in
> this file were fixed before the first run (2026-10-29) so the numbers
> could not be shaped by the format after the fact. Two full runs were
> made: a first run on 2026-10-29/30 that exposed a systematic
> name-transliteration failure, and a re-run on 2026-10-30 after a
> deterministic comparator fix. Both are reported — the headline
> tables are the post-fix system; the pre-fix numbers appear in the
> before/after section, because they are the reason the fix exists.
> Physical-capture sets have not been captured yet; that batch is

## Setup

- Dates of run: first run 2026-10-29/30; post-fix re-run 2026-10-30.
- Repo commits: first run at the pre-fix head (before `484e013b`);
  post-fix re-run at `21c54143`.
- Reader(s): Muse Spark — route A: `muse-spark-1.3` via the Meta Model
  API (hosted); route B: Muse Spark Open (`meta-models/muse-spark-open-1026`)
  via Baseten (open weights). Results are reported per route, never
  blended.
- Reader calibration: Meta route `max_tokens` 1024,
  `reasoning_effort` "minimal" (Muse Spark is a reasoning model; a
  small budget is consumed by reasoning and returns null content).
  Baseten route sends no reasoning-effort parameter — Spark Open
  always reasons at full depth — and needed a much larger completion
  budget: `BASETEN_MAX_TOKENS` 4096 for the first run's re-run, 8192
  for the post-fix run, and a final mop-up pass at 16384 for the sets
  that still returned no content (see Failure analysis).
- Segmenter: SAM 3.1 hosted on the Meta Model API
  (`MetaSAMSegmenter`) in all reported runs. (A self-hosted Modal SAM
  app also exists in the repo but was not used: the owner's Modal
  workspace cannot add the payment method its GPU functions require.)
- Segmentation prompts: fixed in advance — "stamp" for the stamp-masking
  investigation view.
- Perturbation views per field: original, zoom, contrast; on
  disagreement, investigation views zoom_tight and stamp_masked,
  with the step order chosen by the model's investigation planner
  (deterministic mask-then-zoom fallback when the planner is
  unavailable).
- Random seed: generator seed base 7 (per-set seed = base + set index).
- All documents synthetic, generated by `generator/generate.py`,
  SPECIMEN-watermarked. No real documents, no real people.

## Data

| Category | n | What it is |
|---|---|---|
| Clean genuine | 12 | One person, three documents, facts agree, uniform formats. |
| Genuine with variation | 10 | Same facts, legitimate differences: name transliteration variants (Mohammad / Md. / Mohammed), Bangla vs Latin digits, different date formats. Must NOT be flagged. |
| Injected discrepancy | 10 | One planted inconsistency per set: swapped DOB digit, swapped ID digit, or mismatched father's name. Must be flagged as Discrepancy. The first 3 carry the stamp over the birth-certificate DOB. |
| Degraded synthetic | 8 | Generator degradations: blur, glare, rotation. Correct outcome is recovery by re-reading, or Unreadable / recapture — never a silent wrong "Consistent". |
| Hindi-script (secondary) | 10 | Same document family, Hindi persona: Devanagari on the birth certificate, Devanagari digits, Latin on the bank form. 4 clean, 3 variation, 2 discrepancy, 1 degraded. Reported separately, never in the headline pools. |
| Physically captured | ~10 planned | **Not yet captured — batch pending, no results.** |

How generated: `generator/generate.py` renders the three documents
(NID, birth certificate, bank form) from one person record per set and
writes `ground_truth.json` — exactly what each document says, which
the verdict is scored against.

## Configurations

1. **Exact-match baseline** — read each field once, compare raw
   strings across documents. No normalization, no re-reads.
2. **Single-pass + normalization** — one read per field, then the
   deterministic normalization (digits, dates, name variants) and
   comparator from `backend/app/`.
3. **Full agent** — perturbation reads with disagreement-triggered
   investigation (planner-chosen zoom / stamp-masked re-reads), then
   the same normalization and comparator.

## Failure analysis

_Every failure of the full-agent configuration, and every run error,
listed individually. Baseline-configuration failures (exact-match
flags nearly every genuine set by design — cross-script raw strings
never match) are enumerated in full in each run's `results.md`
summary under `eval/results/`._

**Post-fix, Meta route (50/50 completed):**
- variation-07, variation-09 (genuine variation): full agent returned
  **Unreadable / request recapture** — the investigation reads never
  reached a unique majority, so the agent asked for a recapture
  instead of guessing. Conservative by design, but two genuine sets
  did not clear.
- discrepancy-03 (stamp over the birth-certificate DOB): both
  baselines returned Unreadable; only the full agent resolved it
  (caught, 10/10 includes this set). Cover-masking a stamp cannot
  reveal print underneath it (see Limitations); the agent's zoom
  reads carried this one.

**Post-fix, Baseten route (42/50 completed):**
- discrepancy-02 and discrepancy-03 (both stamp over DOB): all three
  configurations returned Unreadable — the planted discrepancy was
  neither caught nor silently passed; the sets end as recapture
  requests. Caught count 8/10 reflects exactly these two.
- degraded-02, degraded-04, degraded-07 (genuine): full agent
  returned Unreadable / recapture after investigation (recovered
  5/8, recapture 3/8 across the category).
- hindi-clean-01 (genuine): full agent false-flagged Discrepancy
  (see Hindi section).
- 8 run errors, all `finish_reason='length'` (the reader returned no
  content within the completion budget): variation-05 plus the 7
  Hindi sets listed above. variation-05 completed in the pre-fix
  Baseten run; its post-fix error is reader variance on the same
  budget, recorded as an error rather than retried indefinitely.

**Pre-fix runs (2026-10-29/30), for the record:**
- Meta route, 39/40 completed (variation-04 lost to an SSL handshake
  timeout): the systematic father-name transliteration failure
  detailed in the next section — 100% of its genuine-set false flags
  (single-pass 29/29 flagged fields, agent 26/26) were the single
  field `father_name` on the birth certificate.
- Baseten route, 39/40 completed (discrepancy-07 returned no content
  even at an 8192 budget): full agent false-flagged 6/22 genuine sets
  — mostly the `name` field on variation sets (noisy Latin reads) —
  caught 8/9 completed discrepancies, silent errors 0. Its first
  attempt at a 1024 budget failed 39/40 sets outright (reasoning
  consumed the budget); the reported run used 4096 with an 8192
  mop-up.

### Name transliteration — before / after the skeleton-equivalence fix

_The dominant failure of the first run (2026-10-29/30), found by
inspecting the per-field reads: every genuine-set false flag on the
Meta route was `father_name` on the birth certificate. That document
renders the name in Bangla (আব্দুল করিম) while the other documents
print Latin "Abdul Karim"; the hosted reader transliterated করিম
back as "Abdul Karami" (26 of 29 genuine sets; also Karomi / Karimi /
Karmi) — never "Abdul Karim" — and the comparator's variant folding
did not bridge the trailing-vowel difference. The misread was stable
across perturbation views, so majority voting could not fix it. The
fix is deterministic, in the comparator's name comparison only
(`backend/app/normalize.py`): folded token lists also match as a
recorded transliteration variant when token counts are equal and
every token pair is equal after folding or shares a consonant
skeleton (vowels removed) with edit distance ≤ 2. It applies to name
fields only — never to ID numbers or dates — and a genuinely
different name (different skeleton, e.g. Karim vs Rahim) still
flags. It was re-measured by re-running both readers over the same
sets; both columns are reported — the pre-fix numbers are not
replaced, they are the reason the fix exists. Denominators differ
between runs because the completed sets differ._

| Metric (full agent, Bangla sets) | Pre-fix — 2026-10-29/30 | Post-fix — 2026-10-30 |
|---|---|---|
| False flags on genuine sets, Meta route (x/n) | 18/21 | 0/22 |
| False flags on genuine sets, Baseten route (x/n) | 6/22 | 0/21 |
| Injected discrepancies caught, Meta route (x/n) | 9/10 | 10/10 |
| Injected discrepancies caught, Baseten route (x/n) | 8/9 | 8/10 |
| Silent errors, both routes (count) | 0 | 0 |

Note what the fix did **not** do: the caught counts did not fall
(Meta 9/10 → 10/10). Skeleton equivalence rescued genuine applicants
without letting a single additional real discrepancy through, on
either route.

## Limitations

- Synthetic data only, rendered by this project's own generator. The
  generator's idea of blur, glare and stamps is simpler than the real
  world's; results on these sets will likely look better than results
  on real captures would. The physically-captured sets will narrow
  that gap but not close it — the underlying documents are still
  synthetic renderings, not real NID cards. That batch is still
  pending, so every number above is synthetic-only.
- Small n: about 10 sets per category, so one case is about 10
  points. Differences of one or two cases between configurations are
  noise, and are described as such. Zero observed events are not a
  zero rate: 0 false flags in 22 genuine sets still allows a true
  false-flag rate up to roughly 3/22 ≈ 14% (rule of three, 95%
  bound), and the same caution applies to the zero silent-error
  counts.
- One document family (Bangladeshi NID / birth certificate / bank
  form, as synthetic approximations) and one base person record with
  variations, plus one Hindi persona. No claim extends beyond that.
- Cover-masking limit: the `stamp_masked` investigation view replaces
  the stamp region with a cover; it cannot reveal print underneath a
  stamp. Fields under a stamp are recovered, when they are recovered,
  by zoom reads of the surrounding print — discrepancy-03 on the
  Baseten route shows the failure end of that limit.
- Route behaviour differs and is reported, not averaged away: the
  hosted reader needed the transliteration fix for Bangla names; the
  open-weights reader's reasoning exceeds practical completion
  budgets on a majority of Devanagari sets.
- **No real-world accuracy claim is made anywhere from this
  evaluation.** It measures the pipeline against its own ground
  truth, on synthetic data, at small sample size.

## Reproduce

The runner is `eval/run_eval.py`. It builds the dataset itself
(fixed seeds), runs all three configurations over the same sets with
the reader the environment selects, and writes results incrementally
— an interrupted run keeps every finished set, and `--resume` skips
sets already completed in the output file (and retries errored ones).

```bash
# From the repo root. One-time setup: python -m venv .venv &&
# .venv/bin/pip install -r backend/requirements.txt pillow pytest
# Route A (hosted):    JUDGE_READER=meta    MODEL_API_KEY=<key>
# Route B (open weights): JUDGE_READER=baseten BASETEN_API_KEY=<key> BASETEN_MAX_TOKENS=8192
JUDGE_READER=meta MODEL_API_KEY=<key> .venv/bin/python -m eval.run_eval --hindi 10 --out eval/results/results-meta-postfix.json
```

- Seed: seed base 7; each set's generator seed is 7 + its index in
  the fixed category order (clean, variation, discrepancy, degraded).
- Dataset: 12 clean + 10 variation + 10 discrepancy (3 of them with
  the stamp over the birth-certificate DOB) + 8 degraded = 40 sets,
  rendered under `eval/data/<set-id>/`, each with its
  `ground_truth.json`. Category counts are configurable
  (`--clean/--variation/--discrepancy/--degraded`, `--scale`).
- Hindi sets: `--hindi 10` appends 10 Hindi-script sets (4 clean,
  3 variation, 2 discrepancy, 1 degraded; set ids `hindi-<category>-NN`,
  seeds continuing the same sequence) rendered from the generator's
  Hindi persona (`generate_set(..., script="hindi")`). They are scored
  through the same three configurations and reported in their own
  summary section (`summary.hindi` in results.json, "Hindi-script
  sets" in results.md) — never in the headline pools.
- Physical batch: the ~10 physically captured sets live under
  `eval/physical/<set-name>/` — the three document photos plus a
  `manifest.json` declaring the expectation (`genuine` /
  `discrepancy` / `degraded`), the differing field for discrepancy
  sets, and the documents' canonical values in the same shape as
  `ground_truth.json`. How to produce them is in
  [`PHYSICAL_CAPTURE.md`](PHYSICAL_CAPTURE.md). The runner ingests
  every well-formed capture folder alongside the synthetic sets
  (`--physical-dir`, default `eval/physical`; a missing or empty
  directory simply adds no sets) and scores them through the same
  three configurations. A capture folder missing a photo or carrying
  a malformed manifest is skipped with a printed warning, never a
  crash.
- Expected output: `eval/results/results.json` (run metadata,
  aggregate counts, and one record per set: per-configuration
  verdict, flagged fields, read values, read count, latency, and
  token/cost figures when the reader reports usage) plus
  `eval/results/results.md`, the same summary rendered in this
  file's table shapes. The numbers are then transcribed into the
  Results tables above — by hand, after the run, never before it.
  The four runs behind this report are `results-meta.json`,
  `results-baseten2.json` (pre-fix) and
  `results-meta-postfix.json`, `results-baseten-postfix.json`
  (post-fix), each with its `.md` summary alongside.
